# Архитектура и инженерные решения

## Компоненты

| Компонент | Версия | Назначение |
|---|---|---|
| PostgreSQL | 17.4 | Источник, logical WAL, `pgoutput` |
| Kafka broker | 4.1.1 | KRaft, журнал событий |
| Kafka Connect | 3.8.0 | Distributed worker с одним экземпляром |
| Debezium PostgreSQL | 3.0.0.Final | Snapshot и чтение WAL |
| Aiven S3 Sink | 3.4.3 | JSONL/Parquet в MinIO |
| MinIO | RELEASE.2025-04-22T22-12-26Z | S3 API и web console; сборка из исходников |
| Kafbat UI | 1.3.0 | Просмотр топиков, consumer groups и задач |
| Python | 3.12 | Генератор, проверка, сценарии, replay |

В `docker/connect/Dockerfile` установлены Kafka runtime и два плагина в
изолированных каталогах `/opt/plugins`. Java 21 удовлетворяет требованиям
Debezium 3.0. PostgreSQL использует `wal_level=logical`; роль `cdc` владеет
таблицами схемы `shop`, имеет LOGIN, REPLICATION и право CREATE на базу,
чтобы Debezium мог создать filtered publication без суперпользователя.

Для брокера задано `KAFKA_JVM_PERFORMANCE_OPTS=-Xshare:off`: это отключает
готовый class archive JVM. При локальной проверке Docker Desktop запуск
с архивом задерживался до готовности брокера; без него брокер стартовал штатно.

## Основной поток

Source читает `shop.orders` и служебную `shop.dbz_heartbeat`. Их топики
раздельные. Sink читает только `cdc.shop.orders`, служебные heartbeat
в файлы заказов не попадают. `decimal.handling.mode=double` выбран для
простого JSON-демо; денежные значения production требуют точной decimal-модели.

Для `orders` установлен `REPLICA IDENTITY FULL`: update/delete несут полный
`before`. Схемы Kafka Connect в основном JSON-потоке отключены.
Ключ события — первичный ключ заказа; записи основного топика не уплотняются.
`tombstones.on.delete=true` сохраняет семантику удаления Kafka.

Один топик имеет одну партицию. Это упрощает сверку последовательности;
масштабирование на несколько партиций требует сохранения стабильной
партиции каждого ключа и независимой обработки offsets каждой партиции.

## Состояние и восстановление

- PostgreSQL volume хранит таблицы, публикации и replication slots.
- Kafka volume хранит журнал, worker offsets, конфигурации и consumer offsets.
- MinIO volume хранит JSONL/Parquet-объекты.
- `.env` хранит локальные credentials; манифесты используют `${env:...}`.
- `artifacts/` содержит генерируемые отчёты, логи и восстановленный JSON.

`down` сохраняет volumes. `up` повторно применяет манифесты через PUT,
имена коннекторов и позиции сохраняются. Начальный snapshot не повторяется
при штатном перезапуске с теми же состояниями. Имя source — часть ключа
сохранённых offsets; имя sink определяет consumer group.

Удаление source не удаляет слот. Cleanup сначала удаляет тестовый
коннектор, затем проверяет неактивность его слота, удаляет слот и публикацию.
Основные слоты этим cleanup не затрагиваются.

## Семантика доставки

Проект не заявляет end-to-end exactly-once. Kafka Connect хранит offsets;
при сбое между внешней записью и подтверждением возможна повторная обработка.
Путь файла содержит топик, партицию и начальный offset. Replay дополнительно
игнорирует уже применённую пару `(partition, offset)` и отклоняет новый
offset ниже ранее обработанного для той же партиции.

Replay рассчитан на конечный набор демо-файлов: строки и увиденные offsets
хранятся в памяти. Для большого журнала потребуется постоянное состояние,
внешняя сортировка или потоковая обработка с checkpoint.

При сравнении генератор остановлен; контрольный заказ проходит после
его остановки. Получение последнего tombstone этого заказа из S3
подтверждает доставку предыдущих записей **в той же партиции**.
Сверяются ключи и бизнес-поля; это не проверка точности всех метаданных времени.

## Heartbeat, WAL и размер файлов

Action heartbeat обновляет одну строку в захватываемой таблице каждые 10 секунд.
Такая транзакция проходит через publication и позволяет источнику подтверждать
WAL даже при простое заказов. Один `heartbeat.interval.ms` без транзакции
в публикации не решает все случаи filtered publication.

WAL слота ограничен 1 ГБ для локального стенда. Если превысить предел,
PostgreSQL может потерять необходимые сегменты; требуется новый согласованный
snapshot, а не попытка продолжить с потерянной позиции.

`offset.flush.interval.ms=10000` установлен у worker, `file.max.records=1000`
у sink. Эти настройки решают разные задачи: интервал задаёт задержку flush,
число записей ограничивает размер отдельного файла. Маленькие файлы при
низкой нагрузке ожидаемы. Для analytics lake нужен отдельный слой compaction.

## Parquet и compaction

Parquet использует отдельные source, слот, публикацию, топик и sink.
Schema/payload включены с самого начала: формат топика не меняется на лету.
`ExtractNewRecordState` оставляет `after`; эксперимент отбрасывает deletes
и tombstone. Этот набор Parquet-файлов показывает формат, его нельзя
считать полным журналом CDC или актуальной таблицей без отдельной модели удаления.

Compaction включена только у отдельного `cdc-stock.shop.stock`. Kafka сохраняет
последние значения ключей в закрытых сегментах, offsets остаются с пробелами.
Активный сегмент не уплотняется; для его закрытия сценарий продолжает обновления.
Количество реально прочитанных записей и разница offsets имеют разный смысл.

## Что требуется для production

Несколько брокеров и workers, replication factor и min ISR, TLS/SASL,
права доступа, внешний secrets provider, актуальные версии, мониторинг
скорости событий, lag и возраста последнего объекта, контроль WAL,
schema contracts, точные decimal, резервирование и тесты восстановления.
